# Troubleshooting: cross-host networking

This is the part most likely to cause trouble, since DC01 and WIN11-CLIENT live on two different hypervisors instead of one.

## Checklist, in order

1. **Can the hosts reach each other at all?** From the Windows host, ping Proxmox's management IP; from Proxmox (`ping` in its shell), ping the Windows host. If this fails, the problem is your physical network, not the VMs — check cabling/switch port, not VirtualBox or Proxmox settings.
2. **Is DC01 actually bridged, not NATed?** In VirtualBox, Settings > Network > Adapter 1 must say "Bridged Adapter" with your real NIC selected, not "NAT." NAT puts the VM behind a private address VirtualBox manages, invisible to the rest of your LAN. Confirm with `ipconfig` on DC01 — it should show 10.50.50.10, not a 10.0.2.x or 192.168.56.x address.
3. **Is WIN11-CLIENT on the right Proxmox bridge?** In the Proxmox VM's Hardware tab, the network device should be attached to vmbr0 (or whichever bridge is tied to the host's physical NIC), not an isolated/internal-only bridge.
4. **Windows Firewall on DC01 blocking the client.** A fresh Server install's firewall will block ICMP (ping) by default and can block DNS/LDAP/Kerberos traffic needed for the domain join if profiles are misconfigured. Confirm the Domain profile is active once DC01 is promoted, and that you're not still on the Public profile (which is far more restrictive). `Get-NetConnectionProfile` shows the current profile; `Set-NetConnectionProfile -InterfaceAlias "Ethernet" -NetworkCategory DomainAuthenticated` if needed.
5. **DNS is the single most common failure point.** The client's only DNS server should be 10.50.50.10 (DC01) — not DC01 plus your router, not DC01 plus 8.8.8.8. A secondary DNS server that isn't DC01 will sometimes resolve `lab.local` queries incorrectly or time out before falling back. Test with `Resolve-DnsName lab.local` and `Resolve-DnsName -Type SRV _ldap._tcp.dc._msdcs.lab.local` from the client; the second one confirms the client can actually locate a domain controller via DNS, which is what the domain join process relies on internally.
6. **Time skew.** Kerberos (which backs domain auth) fails if client and DC clocks are more than 5 minutes apart. Since these are two different physical hosts, this is more likely than in a single-hypervisor lab. Check `w32tm /query /status` on both; after joining, the client should sync time from the DC automatically, but verify it isn't drifting beforehand.
7. **MAC/ARP oddities with bridged adapters.** Some consumer routers and switches are picky about multiple MACs appearing to originate from one physical port (which is what a bridged VirtualBox adapter does). If the Windows host can reach Proxmox but DC01 itself can't be pinged from elsewhere on the LAN, try "Promiscuous Mode: Allow All" on the VirtualBox adapter's advanced settings, and confirm your switch isn't doing port security that drops multiple MACs on one port.

If you get through steps 1–6 and it still isn't working, capture `ipconfig /all` from both VMs and `Resolve-DnsName` output and work backward from there — in practice, it's almost always #2 (NAT instead of Bridged) or #5 (wrong/extra DNS server) in a split-host lab like this.
